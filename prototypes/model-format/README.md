# Prototype: own Schema vs JSON Graph Format profile

Throwaway. It exists to answer one question from the Drakon Editor wayfinder map, under the ticket **Model shape: tree or graph** (Q2, "Adopt an existing format, or write our own?"):

- **Option A: own Schema.** drakonwidget concepts with cleaned-up naming, plus two borrowed patterns: BPMN's separate, id-linked layout section, and a published `$id` and version.
- **Option B: JSON Graph Format (JGF) v2.1 profile.** Valid JGF, with every DRAKON concept in node/edge `metadata` and exits as edges distinguished by `relation`.

Both are graph-shaped on purpose, so the tree-vs-graph question (Q1) stays separate.

## Run it

```sh
npm install
npm run compare
```

## Files

- `samples/expense-claim.own.json`: a realistic Diagram (3-branch silhouette, question, select with 3 cases, FOR loop, insertion, shelf, duration, addresses, a partial layout section, a `meta` bag) written in option A by hand.
- `samples/expense-claim.jgf.json`: the same Diagram in option B, generated by `toJgf`.
- `schema/own.schema.json`: option A's Schema.
- `schema/jgf-profile.schema.json`: option B's profile. It extends the vendored JGF core, `schema/jgf-v2.1.schema.json`.
- `lib.mjs`: the converters `toJgf`/`fromJgf`, `checkModel` (the checks no JSON Schema can do), and Mermaid emitters.
- `compare.mjs`: the harness. It writes `out/broken-report.md`, `out/own.mmd` and `out/generic-jgf.mmd`.

## The same Icon, both ways

Option A puts an Icon and its exits in one place:

```json
"has-receipt": { "type": "question", "text": "Receipt attached?", "yes": "amount", "no": "reject", "down": "yes" }
```

Option B splits it into one node plus edges further down the file:

```json
"has-receipt": { "label": "Receipt attached?", "metadata": { "drakonType": "question", "down": "yes" } }
...
{ "source": "has-receipt", "target": "amount", "relation": "yes" },
{ "source": "has-receipt", "target": "reject", "relation": "no" }
```

## Results

- Both formats hold the sample. It validates against both schemas, and B also validates against the JGF v2.1 core schema.
- The round trip A → B → A is **lossless**. The two options differ only in how easy they are to read and validate, not in what they can express.

Size:

| | own (A) | JGF profile (B) |
|---|---|---|
| minified bytes | 1883 | 3562 |
| JSON values | 110 | 219 |
| pretty-printed lines | 142 | 302 |
| schema lines | 180 | 108 + JGF core 139 |

Which layer catches each deliberately broken Diagram. "Schema" means plain JSON Schema validation is enough; "code" means a custom validator is needed:

| fault | own (A) | JGF profile (B) |
|---|---|---|
| unknown Icon type | schema | schema |
| action without text | schema | schema |
| question missing its 'no' exit | schema | code |
| question missing exit orientation (down) | schema | schema |
| insertion without target Diagram id | schema | schema |
| select with only one case | schema | code |
| dangling reference | code | code |
| loop start not paired with a loop end | schema | code |
| unknown field on an Icon (typo `colour`) | schema | schema |
| action with two `next` exits | cannot be written | code |
| two cases with the same order | cannot be written | code |

## What this shows

1. **Validation.** A catches 8 of the 9 faults both formats can express by schema alone; B catches 5. In B, exits are edges in a separate array, and JSON Schema cannot correlate an edge with its source node. That means it can't check "a question has exactly one `yes` and one `no`" or "a select has at least 2 cases". A also makes two whole fault classes **unwritable**: duplicate exits and ambiguous case order. Both options need code for reference integrity, and for the Grammar in general.
2. **Readability and diffs.** B is about twice the size. Editing one Icon in B touches two places: the node, and its edges somewhere in the `edges` array. In A it touches one object. This matters for a Text view that can show the Model, and for reviewing Diagram changes in git.
3. **Being standard.** B's real benefit is that a tool which knows only JGF can draw *a* graph with no DRAKON knowledge (`out/generic-jgf.mmd`). But that graph has no DRAKON meaning: branches and addresses become plain boxes, and question exit orientation is lost. JGF's ecosystem is small. Option A needs one small table, `exitsOf` in `lib.mjs` (about 10 lines), to do the same. And `toJgf` is about 25 lines, so **JGF can be an export plugin** rather than the Model.
4. **Layout.** Both keep coordinates in a separate, id-keyed section. In B it can only go in `graph.metadata`, which the JGF core leaves untyped. Branches and Icons also share one node namespace in B.

Leaning: **A as the Model, with JGF offered as an export** next to Mermaid and BPMN.

## React to this

The prototype is for reacting to. These are the questions for the grilling session:

1. Open `samples/expense-claim.own.json`. Do the names read well: `next`/`yes`/`no`/`down`/`cases`/`end`/`branch`, `secondaryText`, `diagram`?
2. A makes two things explicit that drakonwidget leaves implicit: an `address` Icon pointing at a branch, and `loopbegin.end` pairing a loop with its end. Keep that?
3. Is "JGF and Mermaid as export plugins" standard enough, or must the Model itself validate as JGF?
4. Branches are an ordered array, each with a `first` Icon. Is that the right top-level shape?
